## Правило №0 — выкладка через GitHub

После того как репозиторий лежит в организации RNV-Development, пуш в ветку `main` сам выкладывает сайт. Это тот же путь, что у Контроля МП: файл `.github/workflows/deploy.yml`, раннер `cxvo` на сервере, секрет GitHub не нужен.

На сервере не затираются `.env`, `bot_api_key.json`, `static/` и `uploads/`. Готовый сайт копируется в `/var/www/cx-dashboard/` без `--delete`. Перед перезапуском проверяется, что код импортируется. Если после перезапуска API не отвечает, код возвращается назад.

Пока репозиторий не в организации, этот файл выкладку не запускает.

Ручная выкладка с Mac ниже — если GitHub-путь не используется.
Сборку из `git archive` не использовать: в таком снимке нет ключей сервера, и сайт уже ломался.

```
✅ npm run build на Mac → rsync в /var/www/cx-dashboard/ (без --delete)
✅ только фронт → службу cx-backend НЕ перезапускать
✅ backend: rsync/scp с Mac → один systemctl restart cx-backend (не весь VPS)
❌ НЕ использовать ./scripts/deploy_committed_release.sh
❌ НЕ собирать сайт из git archive
```

Согласованный порядок («пункт 1»): фронт отдельно от бэкенда. Фоновые синки
крутятся в `cx-bg.service`, не внутри uvicorn. Blue-green не делаем.

На сервере не трогать и не затирать:

- `/root/cx-dashboard/.env`
- `/root/cx-dashboard/bot_api_key.json`
- `/root/cx-dashboard/static/`
- `/root/cx-dashboard/uploads/`

После выкладки бэкенда каталог `/root/cx-dashboard` должен оставаться проходимым
для nginx (`chmod 711 /root/cx-dashboard`), иначе пропадут фото.

## Часть 1: Деплой фронтенда

### Шаг 1 — Собери фронт локально

Открой терминал на Mac и выполни:

```bash
cd /Users/user/Documents/ПРОЕКТЫ/local/cx-dashboard/frontend
npm run build
```

Результат будет в папке `frontend/dist/`.

### Шаг 2 — Загрузи на сервер

```bash
rsync -avz \
  /Users/user/Documents/ПРОЕКТЫ/local/cx-dashboard/frontend/dist/ \
  root@72.56.240.22:/var/www/cx-dashboard/
```

> **Без `--delete`.** Старые hashed JS/CSS оставляем: телефон (Safari/Яндекс) часто держит старую страницу и без старых файлов зависает. Службу `cx-backend` после одного фронта не трогать.

### Шаг 3 — Проверь в браузере

Открой `https://cxvo.ru` → убедись, что страница обновилась.

На компьютере при старой версии — `Ctrl+Shift+R`. На телефоне — полностью закрыть вкладку и открыть заново (не иконка «на экран Домой»).

### Частые проблемы фронта

| Проблема | Решение |
|----------|---------|
| Белый экран | Проверь nginx: `ssh root@72.56.240.22 "nginx -t"` |
| 404 на страницах | Убедись, что nginx настроен на `try_files $uri /index.html` |
| Старая версия / телефон долго грузится | Закрыть вкладку целиком; не `--delete` при rsync |

## Часть 2: Деплой бэкенда

### Обязательная настройка nginx для вложений в чатах

Для `POST /api/v1/cx-responses/{mp}/chats/{id}/message-with-files` установите
в серверном блоке nginx:

```nginx
client_max_body_size 31m;
```

После изменения выполните `nginx -t` и reload nginx. Backend дополнительно
проверяет `Content-Length`, число файлов, фактический формат и размер каждого
файла, но эта проверка **не заменяет** лимит reverse proxy и не предотвращает
чтение chunked-запроса без `Content-Length` самим ASGI-сервером.

### Правило — полный комплект (инцидент 2026-09-10)

Не выкладывать `main.py` без файлов, которые он вызывает при старте.

2026-09-10 ~11:18 МСК: на сервер уехал `main.py` с вызовом `ensure_packaging_review_templates`, а `cx_responses.py` с самой функцией — нет. Uvicorn-воркеры падали при старте, systemd оставался `active`, порт 8001 пустой. Сайт открывался, API отдавал HTML 502 → «Unexpected token '<'» и пустая страница.

Перед рестартом на сервере:

```bash
cd /root/cx-dashboard && PYTHONPATH=/root/cx-dashboard ./venv/bin/python -c "from backend.main import app"
```

Схема БД живёт в `backend/schema.py` (не в `main.py`). Выкладывать **вместе** с `main.py`. Можно прогнать отдельно, без рестарта — идемпотентно, как обычный старт:

```bash
cd /root/cx-dashboard && PYTHONPATH=/root/cx-dashboard ./venv/bin/python -m backend.schema
```

Если эта команда упала — **не рестартить**. Старый процесс продолжает работать.

После рестарта мало `systemctl is-active`. Нужно:

```bash
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8001/docs
ss -lntp | grep 8001
```

Код должен быть `200`, на 8001 должны слушаться **воркеры**, не один мастер. Если 502 снаружи и `Connection refused` на 8001 — смотреть `backend.log` (часто `AttributeError` / нет функции).

## Часть 3: Деплой воркеров

Воркеры — это Python-скрипты, которые запускаются через cron. Они не требуют перезапуска сервиса.

### Обновить воркер (например, worker.py)

```bash
scp /Users/user/Documents/ПРОЕКТЫ/local/cx-dashboard/worker.py \
    root@72.56.240.22:/root/cx-dashboard/

# Или ym_worker.py:
scp /Users/user/Documents/ПРОЕКТЫ/local/cx-dashboard/ym_worker.py \
    root@72.56.240.22:/root/cx-dashboard/
```

### Проверить расписание cron

```bash
ssh root@72.56.240.22 "crontab -l"
```

### Текущее расписание

```cron
# WB воркер
0 */2 * * *  cd /root/cx-dashboard && python3 worker.py hourly   # no-op с июля 2026, можно убрать (см. 01_ОБЗОР_СИСТЕМЫ.md §6)
0 3 * * *    cd /root/cx-dashboard && python3 worker.py daily

# ЯМ воркер
0 23 * * * PYTHONPATH=/root/cx-dashboard /root/cx-dashboard/venv/bin/python3 /root/cx-dashboard/ym_worker.py hourly
*/20 * * * * PYTHONPATH=/root/cx-dashboard /root/cx-dashboard/venv/bin/python3 /root/cx-dashboard/ym_worker.py questions
*/20 * * * * PYTHONPATH=/root/cx-dashboard /root/cx-dashboard/venv/bin/python3 /root/cx-dashboard/ym_worker.py returns
0 3 * * *    PYTHONPATH=/root/cx-dashboard /root/cx-dashboard/venv/bin/python3 /root/cx-dashboard/ym_worker.py daily
0 5,11 * * * PYTHONPATH=/root/cx-dashboard /root/cx-dashboard/venv/bin/python3 /root/cx-dashboard/ym_worker.py reports

# OZON воркер
0 */2 * * *  cd /root/cx-dashboard && python3 ozon_worker.py hourly
0 3 * * *    cd /root/cx-dashboard && python3 ozon_worker.py daily

# Заказы и продажи → Google-таблица (09:00 МСК = 06:00 UTC)
0 6 * * * PYTHONPATH=/root/cx-dashboard /root/cx-dashboard/venv/bin/python3 -m backend.marketplace_daily_sheet >> /root/cx-dashboard/marketplace_sheet.log 2>&1

# ПВЗ: прибыло на ПВЗ → лист InputAPIRustamWB (07:10 МСК = 04:10 UTC)
10 4 * * * PYTHONPATH=/root/cx-dashboard /root/cx-dashboard/venv/bin/python3 -m backend.wb_pvz_input_sheet >> /root/cx-dashboard/wb_pvz_input.log 2>&1

# Системный монитор → Telegram (08:30 МСК = 05:30 UTC)
30 5 * * *  PYTHONPATH=/root/cx-dashboard /root/cx-dashboard/venv/bin/python3 /root/cx-dashboard/system_monitor.py digest >> /root/cx-dashboard/monitor.log 2>&1
*/5 * * * * PYTHONPATH=/root/cx-dashboard /root/cx-dashboard/venv/bin/python3 /root/cx-dashboard/system_monitor.py health >> /root/cx-dashboard/monitor.log 2>&1
```

> ⚠️ Кроны запускаются venv-питоном `/root/cx-dashboard/venv/bin/python3` (в системном `python3` нет sqlalchemy).

> 🔒 **Защита от повторного запуска.** `worker.py`/`ym_worker.py`/`ozon_worker.py` берут Postgres advisory lock при старте (`backend/cron_lock.py`, тот же механизм, что и лидер-election в `backend/main.py`). Если предыдущий запуск того же скрипта ещё не завершился — новый процесс сразу пишет в лог «пропуск» и выходит с кодом 0, не трогая данные. Это касается и ручных запусков из этого раздела: если увидите такое сообщение — где-то уже выполняется этот же воркер, ждать заново не нужно.

### Запустить воркер вручную (для теста)

```bash
ssh root@72.56.240.22
cd /root/cx-dashboard
python3 worker.py daily
```

> `worker.py hourly` для теста запускать бессмысленно — это no-op (см. примечание выше). Претензии/отзывы/вопросы WB синхронизируются фоново внутри backend (`wb_mini_sync.py`, раз в 5 мин) и вручную через CLI не запускаются — перезапустите `cx-backend.service`, если нужно форсировать.

### Резервные копии базы

Каждую ночь в 02:00 UTC (05:00 МСК) `scripts/backup_db.py` снимает копии всех
баз сервера в `/root/backups/db/`: CX, Контроль МП, Навигатор и полка
(`shared_facts`). По каждой базе хранятся 14 последних ночных копий и по одной
на первое число месяца (`monthly/`). Копия CX ~260 МБ. Сбой одной базы не
отменяет остальные.

Скрипт сам проверяет снятую копию через `pg_restore --list`: битый или
оборванный дамп удаляется, а в Telegram уходит тревога. Плюс `system_monitor.py
health` каждые 5 минут смотрит, не старше ли последняя копия 30 часов — так
видно и то, что скрипт вообще не запустился.

```bash
# проверить состояние копий
ssh root@72.56.240.22 "cd /root/cx-dashboard && PYTHONPATH=/root/cx-dashboard ./venv/bin/python3 scripts/backup_db.py --check"

# снять копию вне расписания
ssh root@72.56.240.22 "cd /root/cx-dashboard && PYTHONPATH=/root/cx-dashboard ./venv/bin/python3 scripts/backup_db.py"
```

**Восстановление.** Разворачивать только в отдельную базу — боевую не трогаем:

```bash
su postgres -c "createdb cx_restore_test"
su postgres -c "pg_restore -d cx_restore_test --no-owner --no-privileges -j 2 /root/backups/db/ИМЯ.dump"
# сверить данные, потом убрать за собой:
su postgres -c "dropdb cx_restore_test"
```

Проверено 14.09.2026: восстановление занимает ~33 с, все 107 таблиц на месте.
Если пишешь новый крон или чистишь диск — `/root/backups/` не трогать.

### Копия вне сервера (Яндекс Диск)

`scripts/backup_offsite.py` в 02:30 UTC (05:30 МСК) заливает уже проверенные
ночные копии всех четырёх баз, фото CX за 14 дней (`photos-ГГГГММДД.tar`) и
архив ключей (`secrets/`). На Диске по каждой базе остаётся то, что есть на
сервере.

Работаем через REST API Диска, **не через WebDAV**: WebDAV Яндекс режет до
16–160 КБ/с (замерено 14.09.2026 — 8 МБ заливались 8,5 минут), на копии базы
это часы. REST выдаёт ссылку на отдельный загрузочный хост без такого лимита.
Фото — посуточно, чтобы обрыв связи не стоил гигабайта. Архивы без сжатия:
внутри jpg, gzip дал бы проценты за минуты процессорного времени.

Доступ — OAuth-токен приложения с oauth.yandex.ru (права `cloud_api:disk.read`,
`disk.write`, `disk.info`), в `/root/cx-dashboard/.env`:

```
YADISK_TOKEN=y0_...
```

**Токен живёт около года** (выдан 14.09.2026). Когда перестанет действовать,
заливка начнёт падать и придёт тревога в Telegram. Обновить: открыть
`https://oauth.yandex.ru/authorize?response_type=token&client_id=<ClientID приложения «Бэкап CX»>`,
скопировать новый токен в `.env`. Верифицировать приложение в Яндексе не нужно —
оно служебное и работает только со своим же аккаунтом.

Скорость Диска неровная: копия базы уходит за 16 с (13 МБ/с), а следующие
файлы Яндекс режет до ~128 КБ/с. Поэтому за один прогон заливается не больше
`BACKUP_MAX_PHOTO_UPLOADS` (по умолчанию 4) архивов фото — за пару ночей
история догоняется сама. Разовый полный прогон:

```bash
ssh root@72.56.240.22 "cd /root/cx-dashboard && PYTHONPATH=/root/cx-dashboard BACKUP_MAX_PHOTO_UPLOADS=14 ./venv/bin/python3 scripts/backup_offsite.py"
```

```bash
# что уже лежит на Диске
ssh root@72.56.240.22 "cd /root/cx-dashboard && PYTHONPATH=/root/cx-dashboard ./venv/bin/python3 scripts/backup_offsite.py --check"
```

### Ключевые переменные

| Переменная | Описание |
|------------|----------|

| `WB_TRIGGER_KEYWORD` | Слово-триггер в чате (по умолч. `#от`) |
| `YM_API_KEY` | API ключ Яндекс Маркет |
| `YM_CAMPAIGN_ID` | ID кампании ЯМ |
| `YM_BUSINESS_ID` | ID бизнеса ЯМ |
| `OZON_CLIENT_ID` | Client ID OZON |
| `OZON_API_KEY` | API ключ OZON |
| `CDEK_CLIENT_ID` | Client ID СДЭК |
| `CDEK_CLIENT_SECRET` | Secret СДЭК |
| `CDEK_FROM_PVZ_CODE` | Код ПВЗ отправки в Казани |
| `S3_ACCESS_KEY` | Ключ доступа к Яндекс Object Storage |
| `S3_SECRET_KEY` | Секрет Яндекс Object Storage |
| `SPREADSHEET_ID_INVOICES` | ID Google Sheet с инвойсами |
| `SPREADSHEET_ID_FINANCES` | ID Google Sheet с финансами |
| `JWT_SECRET` | Секрет для подписи JWT токенов |
| `DATABASE_URL` | Строка доступа к Postgres (с паролем). Если не задана — берётся запасное значение из `backend/database.py`. На сервере лучше прописать в `.env` и не держать пароль в коде. |
| `TSHOPPING_MAIL_USER` | Ящик Т-Шопинга, обычно `help@vidovito.team` |
| `TSHOPPING_MAIL_PASS` | Пароль приложения Яндекса для IMAP/SMTP (не основной пароль) |


## Часть 8: Системный монитор → Telegram

Файл `system_monitor.py` шлёт в Telegram два потока:

1. **Утренний дайджест** (`digest`, крон `30 5 * * *` = 08:30 МСК) — собирает
   из таблицы `system_logs` все ошибки крон-воркеров и ИИ-тегирования за 24 ч,
   группирует и шлёт отчёт админу и модератору. Если сбоев нет — короткое «✅ всё чисто».
2. **Контроль «боя»** (`health`, крон `*/5 * * * *`) — проверяет доступность
   сайта/бэкенда, БД и свежесть крон-воркеров. При падении сразу шлёт алерт
   админу И модератору; при восстановлении — сообщение «снова в строю».
   Антиспам: повторное напоминание не чаще раза в 30 мин.

### Настройка (один раз)

Добавь в `/root/cx-dashboard/.env`:

```env
TG_ADMIN_CHAT_ID=123456789          # chat_id администратора
TG_MODERATOR_CHAT_ID=987654321      # chat_id модератора
# Отправка идёт через тот же Cloudflare Worker, что и cx_alert (CF_WORKER_URL).
# Если хочешь слать напрямую своим новым ботом — добавь его токен:
# TG_ALERT_BOT_TOKEN=123456:ABC...
```

> Как узнать `chat_id`: напиши боту любое сообщение и открой
> `https://api.telegram.org/bot<TOKEN>/getUpdates` → поле `"chat":{"id":...}`.

### Деплой

```bash
scp /Users/user/Documents/ПРОЕКТЫ/local/cx-dashboard/system_monitor.py \
    root@72.56.240.22:/root/cx-dashboard/

# Проверить вручную (сразу увидишь сообщение в ТГ):
ssh root@72.56.240.22 "cd /root/cx-dashboard && python3 system_monitor.py digest"
ssh root@72.56.240.22 "cd /root/cx-dashboard && python3 system_monitor.py health"

# Добавить два крона (см. блок расписания выше) через: crontab -e
```

> ⚠️ Прямой доступ к `api.telegram.org` с RU-сервера может быть заблокирован —
> поэтому отправка по умолчанию идёт через Cloudflare Worker. Чтобы новый бот
> слал сообщения, его токен должен быть прописан в самом Cloudflare Worker
> (либо задай `TG_ALERT_BOT_TOKEN` — скрипт попробует прямую отправку, а при
> блокировке автоматически откатится на CF Worker).

## Часть: поддержка Т-Шопинга (почта + Telegram)

Заявки Т-Шопинга приходят на `help@vidovito.team` с адреса
`lifestyle_service@emails.tinkoff.ru`. Фон (`cx-bg`) забирает письма по IMAP,
кладёт в раздел **Запросы «Т-Шопинг»**. Ответ с сайта уходит через SMTP
**с той же почты**, в ту же переписку.

В `.env` на сервере:

```
TSHOPPING_MAIL_USER=vidovito.team/mursalimov/help
TSHOPPING_SMTP_USER=mursalimov@vidovito.team
TSHOPPING_MAIL_PASS=...пароль приложения Яндекса, без пробелов...
TSHOPPING_MAIL_FROM=help@vidovito.team
TSHOPPING_MAIL_ALLOWED_FROM=lifestyle_service@emails.tinkoff.ru,lifestyle_service@tbank.ru
```

Бот `@cxvidovito_bot` по-прежнему может принимать заявки, если им пользуются.
Ответ из бота приходит с пометкой «По заказу …». Имя бота в BotFather не менять
скриптом.

После выкладки бэкенда один раз поставить webhook и команды меню (лучше с Mac),
если нужен ещё и бот:

```bash
# токен не печатать в чат — только в окружение
export TG_ALERT_BOT_TOKEN='…из /root/cx-dashboard/.env…'
python3 /Users/user/Documents/ПРОЕКТЫ/local/cx-dashboard/scripts/set_tshopping_webhook.py
```

Проверка почты: письмо от Т-Шопинга на https://cxvo.ru/tshopping, ответ с сайта
приходит им на почту с `help@vidovito.team`.

Проверка бота: в боте `/start` — меню «Оставить заявку», затем номер заказа.

## Часть: внешний монитор (последняя линия)

`system_monitor.py` живёт на самом сервере — если умрёт весь VPS, его алерты
тоже замолчат. Поэтому снаружи, на Cloudflare, работает независимый сторож:
Worker `lingering-recipe-b1b3` по расписанию (каждые 2 минуты) пингует
`https://cxvo.ru/api/v1/health/live` и пишет в Telegram, если сайт не отвечает.
Код — `cloudflare/telegram-worker.js` (функция `runMonitor`), тесты логики —
`cloudflare/monitor.test.mjs` (`node --test`).

Настройка в панели Cloudflare (один раз):

1. **Workers → lingering-recipe-b1b3 → Edit code** → вставить содержимое
   `cloudflare/telegram-worker.js`, задеплоить.
2. **Settings → Triggers → Cron Triggers → Add** → `*/2 * * * *`.
3. **Settings → Variables** → добавить `MONITOR_CHAT_ID` = chat_id админа
   (тот же, что `TG_ADMIN_CHAT_ID` на сервере). `TG_BOT_TOKEN` уже есть.
4. (Желательно) **Storage & Databases → KV** → создать namespace, затем
   **Settings → Bindings** привязать его как `CX_MONITOR`. С KV тревога
   приходит один раз при падении, раз в час — напоминание, и «снова в строю»
   при восстановлении. Без KV сторож шлёт тревогу на каждом провальном тике.

Проверка: временно поставить в коде `HEALTH_URL` на заведомо мёртвый адрес,
дождаться тика — должно прийти «🔴 Внешний монитор…». Вернуть обратно.
